# S1: Bun Worker maturity

## Question
Does Bun's `Worker` hold up under Flowbun's usage pattern (one OS-thread `Worker` per running block instance, frequently spawned/terminated, passing structured message envelopes)?

## Method
Built 5 standalone scripts in this directory, run individually with `bun run <file>.ts` on Bun 1.3.13 (Linux aarch64, Asahi Fedora, `uname -r` 7.0.13-400.asahi.fc43.aarch64+16k):

- `worker-echo.ts` — shared worker used by most tests; receives `{ type, at, payload }` envelopes and replies with `ping`->`pong`, `relay`->`relay-reply` (verbatim echo), `throw` (throws), `spin` (busy loop), `noop`.
- `idle-memory.ts` — spawns 25 workers, waits for each to post `ready`, measures parent `process.memoryUsage().rss` before/after (with `Bun.gc(true)` to settle). Run twice as separate process invocations: default options and `{ smol: true }`.
- `structured-clone.ts` — round-trips a payload with nested objects/arrays/a `Date` through a worker and back, checks deep equality + non-reference-identity + `Date` type preservation; also verifies sending a function throws.
- `leak-loop.ts` — 300x (spawn worker -> wait ready -> send 3 ping/pong messages -> `terminate()`), sampling RSS every 20 iterations. Run twice: no delay between cycles, and with a 50ms settle delay after each `terminate()` (to separate "async teardown lag" from "real per-cycle growth").
- `failure-modes.ts` — (a) sends a `throw` message, checks the parent `error` event and whether the worker still responds afterward; (b) sends a `spin` (infinite loop) message, calls `terminate()`, and verifies the loop actually stopped two ways: the parent can spawn+use a fresh worker within a 5s hard cap, and (more rigorously) the specific OS thread's CPU ticks (`/proc/<pid>/task/<tid>/stat`) stop increasing after `terminate()`.
- `sqlite-worker.ts` / `sqlite-in-worker.ts` — worker imports `bun:sqlite`, opens an in-memory DB and a temp-file DB, runs a create/insert/select, reports back; host checks it doesn't crash the process.

Key discovery during setup: Bun `Worker`s are **threads inside the same OS process**, not separate processes (confirmed via `/proc/<pid>/task` listing showing new thread IDs appear per worker, PID unchanged). This means `process.memoryUsage().rss` in the parent already captures all worker memory — there's no separate per-worker PID to inspect.

## Results
- Idle memory per worker (default): ~5.5 MB (137.5 MB / 25 workers; baseline 35.8 MB -> 173.3 MB after spawning 25 idle workers; reproduced twice, both ~5.50 MB)
- Idle memory per worker (smol): ~5.5 MB (138.5 MB / 25 workers; baseline 35.3-35.8 MB -> ~174 MB; reproduced twice, both ~5.54 MB) — **no measurable difference from default** for genuinely idle workers; see Notes.
- postMessage/structuredClone fidelity: PASS. Round-tripped nested object/array/`Date` payload was structurally deep-equal to the original, confirmed to be a distinct object (not a shared reference), and the `Date` instance survived as a real `Date` (not stringified). Sending a payload containing a function threw synchronously (`"The object can not be cloned."`) rather than silently dropping or corrupting data.
- terminate()/restart over ~300 cycles: RSS trended **upward, did not plateau**. No-delay run: 35.8 MB -> 121.2 MB over 300 cycles (avg of last 3 samples 117.3 MB vs avg of first post-warmup 3 samples 74.6 MB = +57.4%). Repeating with a 50ms settle delay after each `terminate()` (ruling out simple async-teardown-lag) gave a near-identical result: 35.3 MB -> 110.0 MB (+59.4%). Growth-per-20-iterations stayed roughly constant (~3-6 MB) rather than decaying toward zero, i.e. it looks like a steady per-cycle cost, not a one-time warmup. 300 cycles ran in ~2.4s (no delay), so this is NOT explained by workers failing to actually spin up/down — something is retained per spawn/terminate cycle. Whether this is a true unbounded leak or allocator fragmentation that would eventually plateau over a much longer run could not be determined within this spike's time budget.
- Worker throw behavior: parent's `error` event fired reliably (100% in testing) with the error text available via `event.message` (note: `event.error` was `null`, unlike browser `ErrorEvent` semantics — a Flowbun host would need to parse `.message`, which is a pretty-printed source-frame dump, not a plain message string). The worker did **not** recover — a follow-up `ping` after the uncaught throw got no `pong` response, i.e. the worker thread's JS execution appears dead after an uncaught exception. It does not auto-restart; the host is responsible for detecting `error` and deciding whether to respawn.
- Worker infinite-loop + terminate(): PASS, and fast. `terminate()` itself returns synchronously (its type is `void`, not a `Promise`, unlike Node's `worker_threads`). Practically, the parent process remained fully responsive and could spawn+use a brand-new worker ~6-7ms after calling `terminate()` (well under the 5s hard cap). More rigorously, we identified the actual OS thread accruing CPU time while the `while(true){}` loop ran (31 ticks in 300ms) and confirmed it accrued **zero further CPU ticks** across four consecutive 500ms sampling windows (2s total) after `terminate()` — i.e. the busy loop genuinely stopped, not just "parent moved on while a thread keeps spinning in the background."
- bun:sqlite in worker: PASS. `import { Database } from "bun:sqlite"` worked inside a worker with no special setup. Both an in-memory (`:memory:`) DB and a temp-file-backed DB supported `CREATE TABLE` / `INSERT` / `SELECT` without error, and the parent process remained usable (verified with a follow-up worker round trip) after the test.

## Verdict
PASS (worker-per-block is viable)

## Notes
- **Biggest open risk, needs follow-up before committing to this architecture at scale**: the RSS growth across repeated spawn/terminate cycles (Result 4 above). It did not clearly plateau in 300 cycles / a few seconds of wall clock, and persisted even when cycles were artificially slowed down with a settle delay, which rules out the simplest benign explanation (worker teardown running asynchronously and just needing more time). A human should re-run `leak-loop.ts` with a much higher iteration count (e.g. 5,000-50,000, outside this spike's ~60s-per-test budget) and/or profile with `valgrind --tool=massif` or Bun's built-in heap snapshotting to determine whether this converges or is unbounded. If it's real and unbounded, the mitigation is worker pooling/reuse (don't spawn a brand-new `Worker` per block execution; reuse a small pool) rather than abandoning worker-per-block entirely.
- `smol: true` made no measurable difference to **idle** memory in this test. Per Bun's docs, `smol` sets JavaScriptCore's small-heap configuration and runs GC more often — its benefit likely shows up under allocation pressure (workers that actually do work and churn objects), not for workers sitting idle right after boot. Worth re-testing under a workload that allocates, not just idle workers.
- Bun `Worker`s are OS threads within the parent's process (verified via `/proc/<pid>/task`), not separate processes — there is no per-worker PID, and a worker's memory is not isolated from the parent's `process.memoryUsage()` view. This is good for our RSS-measurement method but means a single catastrophic worker-side crash (e.g. a native segfault, not a JS exception) could in principle take down the whole process; this spike only tested JS-level uncaught exceptions and infinite loops, not native crashes.
- `ErrorEvent.error` being `null` and `.message` being a full pretty-printed source snippet (rather than a bare message) is a minor Bun quirk worth knowing when building real error-handling/logging around worker failures.
- All numbers above are from a single development machine (Apple Silicon under Asahi Linux, aarch64) and a handful of repetitions — treat as directionally solid (idle-memory numbers were reproduced twice each with <1% variance) but not as precise production capacity-planning figures. Re-verify on whatever OS/hardware Flowbun will actually deploy to, especially the leak-loop trend, before finalizing the worker-per-block design.
- Test code lives entirely in `spikes/s1-worker-maturity/` as its own standalone Bun package (`bun init -y` was run here; this directory has its own `package.json`/`bun.lock` and was never wired into the root Flowbun workspace).
